# Controller, Service, Repository: 3계층 구조 이해하기
참고 출처 : https://hianna.tistory.com/1170

 ** 먼저 각자의 역할은 절대 섞이면 안된다 **

레스토랑에 비유

## Controller
웨이터. 주문을 받음.
1. 메뉴가 메뉴판에 있는지 검사.(유효성 검사)
2. 주방(Service)으로 메뉴를 넘김
3. 요리가 나오면 손님에게 서빙(Response)
- 주의 : 절대 요리(비지니스 로직)를 직접하지 않음.


## Service
주방장. 요리를 함(비지니스 로직을 구현)
1. 웨이터(Controller)의 요청을 받고 요리를 시작함
2. 쟤료가 필요하면 창고지기(Repository)에게 요청함
3. 쟤료를 요리함(데이터 가공, 계산, 로직 수행)
- 핵심 : 프로그램의 `지능`이 모여있는 곳임. 코드가 가장 많고 중요함.


## Repository
창고지기. 쟤료 관리가 주 업무(DB접근, 데이터 관리)
1. 데이터베이스(창고, 냉장고)문을 여닫음.
2. 주방장의 요청에 따라 쟤료를 꺼내줌(SELECT)
3. 쟤료 사용 후 저장을 요청하면 저장함(INSERT)
- 핵심 : 어려운 SQL을 직접 짜지 않아도 되게 도와주는 역할(JPA)

데이터는 항상 이 방향으로 돌아감
사용자 → Controller → Service → Repository → DB

## Dto는 또 뭐야?
서빙카트.
- 손님이 주문한 데이터나, DB에서 꺼낸 데이터를 이리저리 옮길 때 내용물이 흐르지 않게 담는 전용 그릇(class)
- 계층 간에 데이터를 주고받을 때는 DTO에 담아서 전달하는 것이 정석입니다.
- Entity는 DB와 밀접한 클래스이기 때문에 메인 코드와 꼭 분리해서 작성해야한다. 안하면 Controller같은거 수정할 때 데이터가 꼬일 수 있음.
